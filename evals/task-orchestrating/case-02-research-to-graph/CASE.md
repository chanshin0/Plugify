# case-02 — 선행 연구·레퍼런스를 실행 결정에 결속한다

## 시험 대상

`task-orchestrating`이 모호한 요구에서 내부 현황 조사와 외부 선행 연구·레퍼런스 조사를 구분하고, 출처 있는 finding을 계약·가정·작업 그래프에 실제로 반영하는지 평가한다. 링크 수집량이 아니라 결정 품질과 추적 가능성을 본다.

## 블라인드 실행 시나리오

각 시나리오는 새 컨텍스트에서 SKILL.md와 필요한 reference만 제공하고 답을 생성한다. ANSWER.md는 실행자에게 제공하지 않는다.

1. 기존 코드와 결정 기록은 확인할 수 있지만 사용자 흐름 선택지가 열려 있는 B2B 알림 설정 화면 요청에서, 내부 현황을 먼저 확인한 뒤 비교 제품·공식 문서의 실제 처리 패턴을 조사하는지.
2. 레퍼런스마다 관찰과 추론을 구분하고, 출처·적용 조건·한계·결정 영향을 남기는지.
3. 조사 결과가 `outcome`, `constraint`, `assumption`, `task:<id>`, `replanWhen` 중 하나 이상과 실제로 결속되는지.
4. 검색 가능한 제품 패턴이나 표준을 사용자 취향 질문으로 둔갑시키지 않는지.
5. 정확한 파일과 수정 내용·검증 명령이 주어진 기계적 이름 변경에서는 ritual browsing 없이 `not_applicable` 사유를 남기고 진행하는지.
6. 서비스 플로우 패턴은 `service-planning`, 되돌리기 비싼 기술 선택은 `tech-deciding`으로 넘기되 조사 질문·프로젝트 제약·기존 근거와 반환 출처를 잃지 않는지.
7. 프로젝트 대외비를 그대로 외부 검색어로 보내지 않고 비식별화하거나 실제 외부 전송 직전에 approval 경계로 분류하는지.
8. 조사 위임을 독립적인 결정 질문에만 사용하고, raw 조사문 대신 결정에 영향을 준 finding만 압축해 지연 없이 실행 계약을 완성하는지.

## 합격

ANSWER.md의 8개 항목을 전부 통과해야 한다. URL 개수·검색 횟수·research task 수는 가산점이 아니며, 출처를 나열했지만 결정이나 그래프가 변하지 않으면 3번은 실패다. 수정 전에도 우연히 일반 웹검색을 했다면 1번 통과로 보지 않고, 구조화된 research brief와 결정 결속까지 확인한다.
