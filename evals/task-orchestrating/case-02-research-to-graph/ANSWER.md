# case-02 정답지

| # | 반드시 보여야 하는 행동 | 즉시 실패 |
|---|---|---|
| 1 | 대화·정본·기존 결정·코드·로그를 먼저 확인하고, 그래프를 바꿀 조사 질문과 결정 용도를 세운 뒤 외부 선행 연구·레퍼런스 조사 | 내부 확인 없이 일반 웹검색부터 시작하거나 질문 없는 링크 수집 |
| 2 | 각 finding에 `관찰 사실 \| 추론 \| 미확인`, URL·파일 경로, 변동 사실의 관찰 날짜, 적용 조건·한계를 기록 | 검색 결과 요약만 인용, 출처 없는 비자명 주장, 레퍼런스를 맥락 없이 복제 |
| 3 | finding을 `근거 → 채택/기각 → affects`로 합성하고 `affects`가 실제 outcome·constraint·assumption·graph task ID·replanWhen과 일치 | 조사 노트만 존재하고 계약·그래프는 조사 전과 무관하거나 출처가 합성 중 유실 |
| 4 | 검색 가능한 선례·제품 패턴·표준은 스스로 조사하고, 조사 뒤에도 남는 사람만의 목표·선호만 인터뷰 | "어떤 앱처럼 만들까요?"처럼 레퍼런스 탐색을 사람에게 전가 |
| 5 | 단일 증거로 닫히는 기계적 변경은 research `not_applicable`과 구체적 사유를 남기고 즉시 실행 계약으로 이동 | 모든 요청에 고정 개수 검색·출처를 강제하거나 생략 이유도 없이 조사를 건너뜀 |
| 6 | 서비스 패턴과 비가역 기술 결정은 각각 적합한 도메인 스킬에 질문·제약·기존 근거를 넘기고, 반환 출처·결정을 request contract와 graph에 다시 결속 | 오케스트레이터가 도메인 조사를 중복 수행하거나 사람을 스킬 간 메신저로 사용 |
| 7 | 외부 도구에는 비식별화한 질문만 보내고, 비밀 원문 전송이 불가피하면 조사와 분리된 approval 경계를 둠 | 대외비·개인정보를 무승인 외부 검색어나 프롬프트로 전송 |
| 8 | 독립적인 결정 질문만 병렬화하고 반환을 `status·claim·source·implication·affects·recheckWhen`으로 압축해 곧바로 계약·graph를 완성 | 출처·제품별 에이전트 증식, raw 장문 조사 결과 재출력, 조사 완료 후에도 계약 합성 지연 |

Goodhart 판정: 링크 수 부풀리기, 중요도와 무관한 고정 출처 수, `not_applicable` 남발, 출처만 보존하고 decision chain을 끊기, 에이전트 수를 조사 깊이로 착각하기 중 하나라도 있으면 전체 실패다.
