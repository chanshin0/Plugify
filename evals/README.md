# evals — 공정(스킬) 문제집

스킬·에이전트·워크플로우가 "잘 동작하는 공정"인지 판정하는 **정답을 아는 시험 세트**. 본사 루프(공정 수정)의 종료조건이다 — 1사례 통과로 출시하지 않는다.

## 언제 돌리나
- **해당 스킬을 수정했을 때** (출하 조건 — `AGENTS.md`). 전 케이스 일괄 아님: 고친 스킬의 문제집만.
- 사고 후 회귀 케이스를 추가했을 때 (그 케이스가 "수정 전 실패 → 수정 후 통과"를 보여야 함).
- (선택) 모델 교체 등 큰 환경 변화 후.

## 케이스 형식
```
evals/<skill>/case-NN-<slug>/
├── CASE.md     # 사용자 요구·수정 전 실패에서 역산한 시험과 합격선
├── ANSWER.md   # 정답지 + 채점표 — 시험 실행 에이전트에게 주지 않는다 (메인/채점자만)
├── setup.sh    # 픽스처를 /tmp 격리 사본으로 부트스트랩 (git init 포함, 결정적)
└── fixture/    # 자급자족 미니 레포 (외부 의존 최소)
```

- `CASE.md`는 사용자 요구와 수정 전 실패에서 합격선을 역산하고, `ANSWER.md`는 실행자에게 숨긴다. 작성 주체가 스스로 green을 확인한 것만으로 confirmed가 되지 않는다. 구현 설명·자기평가·의도를 받지 않은 fresh/blind reviewer가 요구 결속, 빠진 실패 모드, Goodhart 우회를 검증하고 판정을 고정한 뒤에만 경로를 `evals/confirmed-cases.txt`에 추가한다. **confirmed의 유일한 기계 판정은 이 레지스트리다.** `status.sh`는 레지스트리와 파일 실재를 대조해 confirmed·draft·invalid를 분리한다.
- 사람은 새 CASE/ANSWER를 routine 채점하지 않는다. 사람 확인이 필요한 경우는 (a) 원래 요구의 의미가 사람만 아는 경우, (b) 명시된 요구를 바꾸는 경우, (c) confirmed 합격선을 완화하는 경우, (d) 권한·보안·비용·비가역 경계뿐이다.

## 채점 원칙
- **채점은 ANSWER.md 대조 + 실상태 확인**(git log·테스트 재실행·산출물 Read) — 실행 에이전트의 보고를 믿지 않는다.
- **합격선 완화 금지**: 공정을 고치는 에이전트가 confirmed 케이스/합격선을 약화시키는 수정은 사람 승인 필수다. 새 기준을 더 엄격하게 하거나 누락된 명시 요구를 추가하는 변경도 fresh/blind reviewer가 기존 정상 동작의 부당한 실패 여부를 먼저 본다.
- **평가기 동결**: 사고 회귀는 구현 전에 수정 전 실패를 확인하고 CASE·ANSWER·pristine fixture·실행 가능한 runner의 hash를 고정한다. fresh/blind reviewer가 요구 결속을 확인한 뒤 레지스트리에 등록하면 구현 주체는 해당 평가 자산과 runner를 수정하지 않는다. 평가 결함이면 구현을 중단하고 별도 diff로 새 독립 reviewer의 재판정을 받는다. 원 요구의 의미 변경·confirmed 합격선 완화는 언제나 사람 승인이다.
- 신규 draft의 결정적 계약 스크립트 green은 **출제 초안의 사전검증**일 뿐 confirmed eval 합격이나 출하 증거가 아니다. 출력 수치는 고정된 테스트 이름/개수 manifest와 일치할 때만 유효하다.
- 실패 = 본사 사이클 재진입(공정 수정 → 재시험). 케이스 결함이 의심되면 구현을 멈추고 원 요구 근거와 함께 독립 재판정한다. 원 요구의 의미 변경이나 완화가 필요할 때만 사람에게 묻는다.
- 비용: 케이스 1회 = 실제 에이전트 실행(수만~수십만 토큰). 그래서 "수정 시에만" 트리거가 기본.

## 사고 → 회귀 케이스
지점에서 사고가 나면(오보고·검수 뚫림·라이브 실패) incident-protocol 절차에 따라 **그 사고를 재현하는 케이스를 여기에 추가**한다. 예: committed 오보고(2026-06-11) → spec-building case-01 의 채점표에 "워크플로우 반환 committed == git 실제" 항목.
