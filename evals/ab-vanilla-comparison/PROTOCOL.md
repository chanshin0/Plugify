# A/B 비교 실험 프로토콜 — Plugify 공정 vs 기본 Claude Code vs 기본 Codex

2026-09-02 초안을 2026-09-03 계획(3단계 확장판)으로 교체한 정본. Phase 1 결과: `RESULTS-phase1.md`. Phase 2 도구: `phase2/`. Phase 3 사전 등록: `phase3/PREREG.md`(팔 구성은 2026-09-09 기준 — A 팔에 Codex 워커 정책 포함).

## 0. 질문

같은 개발 과제를 줬을 때 Plugify 공정(task-orchestrating → spec-building 그래프 → 블라인드 리뷰 → live-verify)이 스킬 없는 기본 Claude Code, 기본 Codex 보다 **무엇이 얼마나** 나은가, 그리고 **얼마를 더 내는가**.

## 1. 재는 것 (5축 + 1)

| 축 | 정의 | 잰 방법 |
|---|---|---|
| Q 결과물 품질 | 동작·엣지케이스·코드·테스트·문서 | 숨긴 테스트 + **사람 눈 블라인드 쌍대 비교**(§4) + 모델 리뷰(보조) |
| A 자율성 | 사람 개입 없이 끝까지 가는가 | 개입 횟수·종류, `terminalState` |
| T 신뢰성 | **보고 ≠ 실제** 건수 (완료 주장 vs git·테스트 실제) | 산출물 스냅샷과 주장 대조 — 이 공정의 존재 이유라 1급 지표 |
| C 비용·시간 | 토큰 $, 벽시계(작업/대기 분리) | 세션 JSONL 집계, Codex usage |
| R 재개 가능성 | 새 세션이 후속 과제를 이어받는가 | "기능 1개 추가" 후속 라운드 성공·시간 |

결론은 축별로 "A−B 차이와 방향"만 적는다. 총점·총평 금지(초안 원칙 유지).

## 2. 방법 3단계 (순서 = 싼 것부터)

### Phase 1 — 문제집 역공격 (거의 공짜)
`evals/` confirmed 케이스는 "공정 없이 하면 실패했던 사고"의 재현 픽스처다. 같은 CASE를 **깨끗한 설정의 기본 Claude Code / 기본 Codex** 로 돌려 ANSWER 채점표 통과율을 비교한다.
- 대상 (공정 성격의 케이스만, 6개): `spec-building/case-01-boundary-bugfix`, `spec-building/case-03-live-gate-preview`, `live-verify/case-01-push-not-real-stop`, `perf-review/case-01-planted-perf-bugs`, `service-planning/case-01-planted-gaps-and-pruned`, `tech-deciding/case-01-target-and-adr-path`.
- 제외: 워크플로우의 반려 계약을 재는 케이스(`spec-building/case-02-no-gate-rejected` 등 — vanilla 에는 "반려"가 없어 비교 불가), 도메인 스킬 케이스(hymn-letter·illustrated-story·install·telemetry·visualize — 그 스킬이 없는 팔에서는 계약 자체가 없다).
- 절차: `setup.sh` 로 격리 픽스처 → 팔별로 CASE.md 의 사용자 요구 문장만 프롬프트로 투입(ANSWER 비공개) → 채점은 ANSWER 대조 + 실상태 확인(기존 규약 그대로).
- 산출: 케이스 × 팔 통과표 + 실패 유형. 러너·채점기: `phase1/`.
- 잰다: 공정이 막는 실패 유형이 vanilla 에서 실제로 재발하는가. **못 잰다**: 평균적 우위(케이스가 공정 실패에서 역산돼 vanilla 에 불리 — 결론에 명시).

### Phase 2 — 실전 로그 관찰 (2~4주, 공짜, 인과 아님)
지점 레포에서 task 마다 `공정 / 직접 편집` 을 태깅하고, 이미 남는 신호를 모은다.
- 신호: spec-building `runSummary`(`terminalState`·`attempts`·`humanReintervention`·`reviewerBlind`), git 되돌림·핫픽스 커밋, live-verify 실패, 세션 비용(`improve-token-efficiency` 가격표).
- **선행 조건**: 가격표 최신화(감사 F1 — 2026-09-04 적용).
- 편향: 쉬운 건 직접, 어려운 건 공정에 넣는 자기선택. 변경 파일 수로 층화해 같은 크기끼리 비교한다.
- 산출: 주간 표(태그별 사고율·재개입·비용/변경 파일). 스크립트: `phase2/weekly-report.py`.

### Phase 3 — 사전등록 A/B 벤치 (비용 큼)
| 항목 | 초안 | 변경 |
|---|---|---|
| 과제 | greenfield 1개 | **3개**: greenfield(쇼츠 규칙 도구) · brownfield 버그픽스(직렬 마스킹형 — 공정이 강한 곳) · 스펙 모호형(가정 문서화 품질) |
| 반복 | 1회 | 과제·팔당 **2회**(분산 관측) |
| 개입 | 승인 경계만 | **1차 봉인**(헤드리스, 승인 자동 허용·질문엔 "스펙대로"), 2차 허용+기록+감점 |
| 팔 | A Plugify / B 기본 Claude Code(깨끗한 CLAUDE_CONFIG_DIR) / C 기본 Codex | 유지. A−B 는 "Plugify + 전역 CLAUDE.md + Codex 워커 정책" 합산 효과임을 명시 |
| 채점 순서 | 게이트 → 결함 → 비용 → 후속 → 루브릭 | 숨긴 테스트 → **보고≠실제** → 사람 눈(§4) → 모델 리뷰(일치율 보고) → 비용·시간 → 후속 과제 |
- 사전 등록(실행 전 커밋): TASK-SPEC 3개, judge 하네스, 사람 평가 차원·앵커, 엣지케이스 3개/과제, 익명화 규칙 — 전부 `phase3/`.
- 규모: 3 과제 × 3 팔 × 2회 = 18회 + 후속 라운드 18회.

## 3. 익명화 (사람 눈 평가의 전제)
제품 층만 남기고 팔 식별 흔적을 벗긴다: `.planning/` 전체, 커밋 트레일러·커밋 메시지, 도구·스킬 언급 문자열, 팔 고유 파일명 관례. 결과를 X/Y/Z 로 재명명하고 매핑은 봉인 파일에 둔다(평가 종료 후 개봉). 공정 층(STATE·ADR)은 익명화 불가 → 제품 층 판정이 끝난 뒤 따로 본다. 도구: `phase3/tools/anonymize.py`.

## 4. 사람 눈 평가 설계
1. **차원 5개를 산출물 보기 전에 고정·커밋**: ① 직접 10분 써봤을 때 동작 ② 사전 등록한 엣지케이스 3개를 견딤 ③ 코드가 설명 없이 읽힘 ④ 테스트가 실제 실패를 잡음(하나 고의로 깨 봄) ⑤ 문서만 보고 새 사람이 기능 하나를 추가할 수 있음.
2. **점수 대신 쌍대 비교**: 쌍마다 "어느 쪽이 나은가 + 이유 한 줄 + 확신도". 순서 무작위. 차원별 승패만 기록, 합산 없음.
3. **순서 고정**: 동작 → 엣지케이스 → 코드 → 테스트 → 문서. 뒤 단계에서 앞 판정을 바꾸지 못한다(코드 취향이 동작 판정을 오염시키지 않게).
4. **자기 노이즈 측정**: 쌍의 30% 를 하루 뒤 재판정. 뒤집힌 비율 = 판정 오차. 팔 간 차이가 이 오차보다 작으면 "차이 없음".
5. **모델 판정은 보조**: fresh opus·codex 블라인드 리뷰의 사람 판정 일치율을 보고. 일치율이 높으면 다음 실험의 1차 필터로 승격.
6. 평가자 1명이면 결론에 "내 기준에서의 우위"라고 적는다. 동료 1명이 쌍 몇 개만 봐줘도 신뢰도가 크게 오른다.
- 도구: **블라인드 리뷰 콘솔** `phase3/tools/review-console.html` — 익명 산출물 2개 나란히, 차원별 선택·이유 입력, 순서 셔플, 재판정 세션, JSON 기록.

## 5. 결과 보고 형식 (`RESULTS.md`)
- 축별 표: 팔 × 과제 × 회차, 셀 = 측정값. 옆에 A−B, A−C 차이와 방향.
- 사람 평가: 차원별 승률 + 재판정 뒤집힘율 + 모델 일치율.
- 비용: 토큰 $ 와 벽시계(작업/대기 분리), 과제당.
- "총평" 섹션 없음. 대신 §7 한계를 그대로 붙인다.

## 7. 결론에 반드시 적을 한계
- Phase 1 은 공정에 유리한 케이스 집합(사고 역산)이다.
- Phase 2 는 인과가 아니다(자기선택). 층화로 일부만 상쇄.
- Phase 3 의 C 팔은 모델 차이가 섞인다(도구 순수 비교는 A vs B). A−B 는 전역 CLAUDE.md·Codex 워커 정책 효과를 포함한다.
- 1차 봉인 실행은 공정의 인터뷰·승인 경계 가치를 재지 않는다(2차에서 개입 허용으로 보완).
- 사람 평가자가 1명이면 "내 기준" 이며, 재판정 오차 이하의 차이는 차이가 아니다.

## 8. 전제·추정 (틀리면 결과가 바뀌는 것만)

- [추정] 순수 Plugify 팔(전역 CLAUDE.md 는 유지, 스킬·에이전트만 제거)은 두지 않고 합산 효과로 보고한다.
- [추정] Phase 3 brownfield 는 실제 지점 레포 버그 대신 **결함을 정확히 통제한 합성 픽스처**(`phase3/tasks/02-brownfield-ledger/fixture`)를 쓴다 — 숨은 결함이 무엇인지 사전 등록할 수 있어야 "직렬 마스킹"을 잴 수 있기 때문.
- [추정] 사람 평가는 사용자 1명 + 가능하면 동료 1명이 일부 쌍.
