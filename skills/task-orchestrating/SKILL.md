# task-orchestrating — 요구 → 조사·연구·인터뷰 → 실행 그래프 → 검증

사용자의 첫 문장을 곧바로 구현 명령이나 질문지로 취급하지 말고, 에이전트가 실행 가능한 계약으로 만든 뒤 끝까지 운전하라. 도메인 스킬을 대체하지 말고 앞단 오케스트레이터로 사용하라.

## 핵심 계약

- 사람에게 요구할 것은 **의도·개인 맥락·선호·권한·비가역 승인**이다.
- 에이전트가 맡을 것은 **현황 조사·선행 연구·레퍼런스 조사·저위험 가정·분해·완료 증거 설계·실행·검증·재계획**이다.
- `Agent Self Turn`을 "새 사용자 메시지 없이 에이전트가 증거를 근거로 다음 의미 있는 상태를 시작한 전환"으로 정의하라. 메시지·도구·서브에이전트 호출 수를 세지 마라.
- 사전에 식별한 인터뷰·승인 전환은 자율성 실패가 아니다. 조사 가능한 사실을 묻거나, 실패 뒤 전략을 바꾸지 못하고 사람에게 떠넘긴 경우는 자율성 누수다.

## 1. 먼저 조사하기

1. 요청에서 원하는 결과·제약·금지·영향 범위를 잠정 추출하라.
2. 현재 대화, 작업 폴더, 프로젝트 정본, 기존 결정·조사 기록, 실제 코드와 로그를 먼저 확인하라. 같은 근거를 다시 수집하지 말고, 오래된 근거는 결과를 바꿀 최신성만 재검증하라.
3. 모르는 항목을 다음 네 종류로 분류하라.

| 종류 | 처리 |
|---|---|
| `discoverable` | 에이전트가 조사한다. 사람에게 묻지 않는다. |
| `assumable` | 결과 영향이 작고 되돌릴 수 있으면 기본값을 택하고 가정으로 기록한다. |
| `human-context` | 사람만 아는 의도·선호·우선순위이며 결과를 바꾸면 인터뷰한다. |
| `approval` | 권한·보안·비용·외부 전송·파괴·비가역 행동 직전에 승인받는다. |

분류 근거와 해결 결과를 요청 기록에 남겨 같은 질문을 반복하지 마라.

### 선행 연구·레퍼런스 조사 게이트

내부 현황 조사 뒤에도 외부 선례·비교안이 `outcome`, `constraints`, `doneWhen`, 가정 또는 작업 그래프를 바꿀 수 있으면 인터뷰 전에 짧은 research brief를 작성하라. 사용자가 명시적으로 연구를 요청한 경우에도 실행하라. 그 외에는 단일 증거로 닫히는 atomic·기계적 작업이나 정본이 선택을 완전히 규정한 작업을 `not_applicable`과 이유를 기록하고 생략하라.

직접 조사하기 전에 소유자를 먼저 정하라. 서비스 플로우·화면·엣지의 비교 제품 패턴은 `service-planning`의 패턴 조사 레인, 되돌리기 비싼 기술 비교·선정은 `tech-deciding`의 축별 조사 레인이 소유한다. 오케스트레이터는 조사 질문·프로젝트 제약·재사용할 선행 근거를 넘기고 반환된 출처와 결정을 brief·graph에 결속하되, 같은 외부 조사를 범용 레인으로 다시 수행하지 마라. 어느 도메인에도 속하지 않는 질문만 여기서 직접 조사하라.

1. 그래프를 바꿀 **조사 질문**과 그 답을 사용할 **결정 지점**부터 적어라. 질문 없는 링크 수집은 금지한다.
2. **선행 연구**에서는 기존 시도·결정·표준·공식 문서·논문·사고 사례를 찾아 무엇이 이미 검증되거나 실패했는지 확인하라. **레퍼런스 조사**에서는 비교 가능한 실제 제품·산출물·코드·워크플로우가 같은 문제를 어떻게 처리하는지 직접 관찰하라.
3. 로컬 정본과 1차·공식 출처를 우선하라. 변동 가능한 사실에는 관찰 날짜를 남기고, 비자명한 주장에는 URL이나 파일 경로를 붙여라. 검색 결과 요약을 근거로 쓰지 말고 `관찰 사실 | 추론 | 미확인`을 구분하라. 사적인 프로젝트 내용을 외부 검색어로 전송해야 한다면 비식별화하고, 그래도 경계를 넘으면 `approval`로 분류하라.
4. 각 finding을 `근거 → 적용 조건·한계 → 채택/기각 결정 → affects`로 합성하라. `affects`는 `outcome | constraint | assumption | task:<id> | replanWhen` 중 하나 이상이며, 그래프에 영향을 주지 않는 참고 링크는 축적하지 마라.
5. 그래프를 바꿀 질문이 근거로 닫혔거나 추가 출처가 결정을 바꾸지 않으면 멈춰라. 단일 출처·최신성·비교 가능성의 한계와 미해결 항목은 숨기지 말고 `recheckWhen`에 남겨라.

조사를 위임할 때는 출처나 제품별이 아니라 서로 독립적인 **결정 질문별**로만 나눠라. 반환 형식을 `status·claim·source·implication·affects·recheckWhen`으로 제한하고, 일반 배경 설명·출처별 장문 요약·중복 패턴은 요청하지 마라. 오케스트레이터는 raw 조사문을 다시 나열하지 않고 결정을 바꾼 finding과 출처만 research brief로 압축한 뒤 바로 계약·그래프 합성으로 넘어가라.

research brief 형식은 [request-contract.md](references/request-contract.md)를 따르라.

## 2. 필요한 것만 인터뷰하기

`human-context` 중 지금 선택하지 않으면 작업 그래프가 크게 달라지는 항목만 질문하라. 관련 질문을 한 번에 1~3개로 묶고 다음을 포함하라.

- 현재 이해와 이미 확인한 사실
- 왜 이 답이 필요한지
- 권장 선택과 이유
- 실질적인 대안·차이
- 답에 따라 달라지는 작업
- 한 문장 질문

"어떻게 할까요?"처럼 분석을 사람에게 넘기는 열린 질문을 금지하라. 답을 기다리는 동안 독립적인 조사·골격·비파괴 작업을 계속할 수 있으면 계속하라. 답을 받으면 `질문 → 답 → 결정 → 영향 task`로 요약하고 별도의 "진행해도 될까요" 없이 그래프를 갱신해 재개하라.

## 3. 실행 계약 만들기

요청이 단일 증거로 닫히는 atomic task면 억지로 쪼개지 마라. 둘 이상의 독립 증거·의존성·위험 경계가 있을 때만 그래프를 만들라. 그래프 전에 다음을 확정하라.

- `outcome`: 사용자가 얻는 결과
- `constraints`: 지켜야 할 경계
- `doneWhen`: 에이전트가 직접 확인할 전체 완료 증거
- `nonGoals`: 이번 범위가 아닌 것

각 task에 반드시 다음을 넣어라.

- `id`, `goal`, `why`
- `targets`: 바꿀 산출물·파일·외부 표면
- `depends`: 선행 task ID
- `evidence`: 에이전트가 실행·관찰할 통과 신호. 코드 그래프는 `{id, kind:"command", run, expect:{exit,outputIncludes,outputExcludes}}` 구조를 쓰고, 실제 종료코드·출력은 오케스트레이터가 다시 판정한다. 승인·육안 확인을 명령 증거로 위장하지 마라.
- `assumptions`: 적용한 저위험 가정, 없으면 빈 배열
- `risk`: `RISKY | MECHANICAL | NONE`
- `replanWhen`: 기존 접근을 버리고 그래프를 바꿀 관측 조건

계획이나 사용자 응답에서 실행 그래프를 보여줄 때는 validator 호환 JSON을 사용하고 모든 필드를 생략하지 마라. 제목·서술 순서가 `why·depends·assumptions`를 암시한다고 간주하지 말고 빈 값은 `[]`로 명시하라. `depends`에는 graph의 task ID만 넣고, 사람 인터뷰·승인은 knowledge map/interview ledger/approval 경계에 별도로 기록하라.

상세 형식과 기록 위치는 [request-contract.md](references/request-contract.md)를 따르라. 계획에는 목표와 완료 조건을 포함하되, 사용자가 체크할 목록이 아니라 에이전트가 닫을 증거로 쓰라.

## 4. 실행하고 재계획하기

1. 의존성이 충족된 task부터 실행하라. 상태를 `pending | in_progress | completed | blocked`로 갱신하라.
2. 각 task의 `evidence.run`을 실행하고 선언한 `id·run`과 실제 `exit·output·passed`를 1:1 대조하라. 자기보고를 증거로 쓰지 마라.
3. 증거 실패나 새 사실이 `replanWhen`에 해당하면 같은 전략을 반복하지 말고 원인·가정·의존성을 갱신해 그래프를 바꿔라.
4. 안전한 대안과 상한을 소진한 뒤에만 사람에게 에스컬레이션하라. 그때는 확인한 사실·시도·막힌 이유·권장 선택을 제시하라.
5. 코드 구현이면 이 계약을 `.planning/STATE.md`의 목표·게이트·그래프로 컴파일한 뒤 `spec-building`에 넘겨라. `auto:` 게이트는 에이전트가 만들고, `human:`은 취향 확인이 아니라 `approval` 경계에만 사용하라.
6. 기획·기술 결정·라이브 검증은 각각 기존 도메인 스킬로 라우팅하되, 사람 답변을 스킬 사이 메신저로 쓰지 마라. 한 답이 오면 오케스트레이터가 다음 상태를 시작하라.

## 5. 닫기

- `doneWhen`과 task별 `evidence`가 모두 실제로 확인됐을 때만 완료로 보고하라.
- 비가역·고위험 결과는 구현자 설명을 가린 fresh/blind 검증을 추가하라.
- 최종 보고에는 결과, 핵심 증거, 남은 승인·한계, 중요한 가정만 남겨라. 사람에게 완료 조건 재검사를 요청하지 마라.
- 의미 있는 전환만 최소 이벤트로 기록하라. 관측할 수 없는 재개입률·사후 누출률·낭비율은 `not_observable`로 두고 추정 점수를 만들지 마라.

## 금지

- 조사 가능한 사실을 사람에게 질문하기
- 조사 질문 없는 레퍼런스 수집, 출처 없는 관찰을 사실로 단정하기
- 조사 결과를 결정·가정·task·재계획 조건 어디에도 연결하지 않고 쌓아두기
- 출처·제품마다 에이전트를 늘리거나 raw 조사문을 운반해 계약 합성을 지연하기
- 사소한 기본값마다 진행을 멈추기
- 완료 조건을 사람이 확인할 체크리스트로 바꾸기
- task 수·호출 수·메시지 수로 자율성을 부풀리기
- 독립 증거 없는 완료, 실패를 advisory로 낮추기, confirmed 합격선 완화하기
